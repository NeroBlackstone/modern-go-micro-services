# Day 13 - 服务间认证：为什么微服务需要互相证明身份？

## 问题：服务间通信是"裸奔"的

Day 10-12 我们完善了**外部请求**的认证链路：

```
Client → Traefik → Oathkeeper（认证+授权） → 后端服务
```

但后端服务之间的调用完全没有认证：

```
order-service ──── gRPC (insecure) ────▶ book-service
                   ↑
              无任何身份证明
              无 TLS 加密
              无 token 传递
```

**这意味着什么？**

1. **任何容器都能伪造请求**：Docker 网络内的任意容器都可以冒充 order-service 调用 book-service
2. **用户身份丢失**：order-service 收到的用户信息（谁下的订单）在调用 book-service 时完全丢失
3. **无法审计**：book-service 不知道请求来自哪个服务、代表哪个用户
4. **无法实施细粒度权限**：book-service 无法区分"order-service 的合法调用"和"恶意请求"

## 服务间认证的核心目标

```
┌─────────────────────────────────────────────────────────┐
│              服务间认证要解决的问题                        │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  1. 身份证明（Authentication）                           │
│     "你是谁？" — 证明调用方是合法的服务                    │
│                                                         │
│  2. 完整性（Integrity）                                  │
│     "消息没被篡改" — 请求内容在传输中未被修改              │
│                                                         │
│  3. 用户传播（User Propagation）                         │
│     "代表谁调用" — 将原始用户身份传递到下游服务            │
│                                                         │
│  4. 审计追踪（Audit Trail）                              │
│     "谁做了什么" — 记录每次调用的来源和目的                │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

## 常见方案对比

### 方案一：mTLS（双向 TLS）

```
order-service                          book-service
    │                                       │
    │  1. TCP 握手 + TLS 协商               │
    │ ◀────────────────────────────────────▶│
    │  2. 双方交换证书                       │
    │ ◀────────────────────────────────────▶│
    │  3. 验证证书链                         │
    │  4. 建立加密通道                       │
    │ ═══════════════════════════════════════│
    │  5. 在加密通道上发送 gRPC 请求          │
    │ ──────────────────────────────────────▶│
```

| 优点 | 缺点 |
|------|------|
| 传输层加密，安全性最高 | 证书管理复杂（需要 CA） |
| 无需修改应用代码 | 不传递用户身份信息 |
| 标准化方案 | 性能开销（TLS 握手） |

### 方案二：OAuth2 Client Credentials

```
order-service          Hydra           book-service
    │                    │                  │
    │ 1. client_credentials grant           │
    │ ──────────────────▶│                  │
    │ 2. access_token    │                  │
    │ ◀──────────────────│                  │
    │                    │                  │
    │ 3. gRPC + Bearer token                │
    │ ──────────────────────────────────────▶│
    │                    │ 4. introspect    │
    │                    │ ◀────────────────│
    │                    │ 5. valid         │
    │                    │ ────────────────▶│
```

| 优点 | 缺点 |
|------|------|
| 标准化 OAuth2 流程 | 每次调用都需要 introspect（延迟） |
| 使用现有 Hydra 基础设施 | 需要管理 client credentials |
| Token 有效期可控 | 增加了对 Hydra 的依赖 |

### 方案三：Shared Secret JWT（本项目采用）

```
order-service                          book-service
    │                                       │
    │ 1. 生成 JWT（HMAC 签名）              │
    │    iss=order-service                  │
    │    aud=book-service                   │
    │    sub=order-service                  │
    │    caller_user=alice                  │
    │                                       │
    │ 2. gRPC metadata: authorization       │
    │ ─────────────────────────────────────▶│
    │                                       │ 3. 验证 JWT 签名
    │                                       │ 4. 检查 aud 匹配
    │                                       │ 5. 提取 caller 信息
    │                                       │
```

| 优点 | 缺点 |
|------|------|
| 实现简单，学习成本低 | 需要安全分发共享密钥 |
| 无外部依赖（不需要 Hydra） | 无法撤销单个 token |
| 低延迟（本地验证） | 密钥泄露影响范围大 |
| 可携带用户信息 | 不提供传输层加密 |

## 为什么选择 Shared Secret JWT

对于学习项目，Shared Secret JWT 是最佳选择：

1. **与现有架构一致**：Oathkeeper 已经在使用 HMAC 签名的 JWT，保持一致
2. **学习重点明确**：gRPC metadata 传播 + 拦截器链 + JWT 签发/验证
3. **无额外基础设施**：不需要配置 Hydra client credentials
4. **代码改动最小**：只需添加拦截器，不需要修改业务逻辑

## gRPC 拦截器链

本项目使用拦截器链模式，服务间认证作为链中的一环：

```
请求发出（order-service）:
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ Tracing │───▶│  Auth   │───▶│Circuit  │───▶│  Retry  │───▶│ Rate    │
│         │    │ (签发)  │    │Breaker  │    │         │    │Limiter  │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └─────────┘
     │              │              │              │              │
     ▼              ▼              ▼              ▼              ▼
  创建 Span    注入 JWT      检查状态       失败重试      限流控制

请求接收（book-service）:
┌─────────┐    ┌─────────┐
│ Tracing │───▶│  Auth   │───▶ Handler
│         │    │ (验证)  │
└─────────┘    └─────────┘
     │              │
     ▼              ▼
  提取 Span    验证 JWT
              提取调用方信息
```
