# Day 9 - 容错模式：为什么微服务需要容错？

## 为什么需要容错？

在微服务架构中，服务故障是**常态**，不是异常。一个用户请求可能经过 5-10 个服务，只要其中一个故障，整个请求就失败。

### 级联故障（Cascading Failure）

```
用户请求 → order-service → book-service (正常)
                          → user-service (故障！超时 30s)
                              ↓
                          order-service 线程阻塞等待
                              ↓
                          所有线程被耗尽
                              ↓
                          order-service 也开始拒绝服务
                              ↓
                          Traefik 返回 502/503
                              ↓
                          用户看到系统不可用
```

一个服务的故障，通过资源耗尽（线程池、连接池）传播到调用方，最终导致整个系统瘫痪。

### 三种故障类型

| 类型 | 特征 | 示例 | 策略 |
|------|------|------|------|
| **瞬时故障** | 持续时间短，自动恢复 | 网络抖动、GC 停顿 | 重试 |
| **持久故障** | 需要人工干预或长时间恢复 | 数据库宕机、磁盘满 | 熔断 + 降级 |
| **过载** | 请求数超过系统处理能力 | 流量突增、大促活动 | 限流 + 背压 |

## 核心容错模式

### 1. Circuit Breaker（熔断器）

**作用**：快速失败，避免无意义的重试消耗资源。

**三态模型**：

```
         失败率 > 阈值
    ┌─────────────────┐
    │                 ↓
 ┌──┴──┐         ┌──────┐
 │CLOSED├────────►│ OPEN │
 └──┬──┘         └──┬───┘
    ↑               │
    │   超时后       │
    │               ↓
    └───────────┌────────┐
                │HALF-OPEN│
                └────────┘
```

- **Closed（关闭）**：正常放行请求，同时统计失败率
- **Open（打开）**：拒绝所有请求，直接返回错误
- **Half-Open（半开）**：允许少量请求通过，测试下游是否恢复

### 2. Retry + Backoff（重试与退避）

**作用**：自动恢复瞬时故障。

**指数退避公式**：
```
backoff = initialBackoff × multiplier^attempt + jitter
```

**关键参数**：
- `MaxRetries`：最大重试次数（避免无限重试）
- `InitialBackoff`：初始等待时间（如 100ms）
- `BackoffMultiplier`：退避倍数（如 2.0）
- `MaxBackoff`：最大等待时间上限（如 2s）
- `Jitter`：随机抖动（防止重试风暴）

**重试风暴问题**：
```
100 个客户端同时失败
  → 同时重试（100ms 后）
    → 服务端收到 200 个请求（更过载）
      → 更多失败 → 更多重试
```

加 jitter 后，重试时间分散在 `[0, backoff*0.1]` 范围内，避免同步重试。

### 3. Rate Limiter（限流器）

**作用**：保护服务不被过载。

**两种经典算法**：

| 算法 | 原理 | 特点 |
|------|------|------|
| **令牌桶** | 按固定速率往桶里放令牌，请求需要取令牌 | 允许突发流量 |
| **漏桶** | 请求进入桶，按固定速率流出 | 平滑流量，不允许突发 |

**令牌桶示例**：
```
Rate = 10/s, Burst = 5

正常流量：  ○○○○○○○○○○  (10个/秒，全部通过)
突发流量：  ○○○○○○○○○○○○○○○  (前5个突发通过，后续限流)
过载流量：  ○○○○○○○○○○○○○○○○○○○  (超过 burst 的被拒绝)
```

### 4. Bulkhead（舱壁隔离）

**作用**：隔离资源，防止一个故障拖垮所有。

**示例**：线程池隔离
```
order-service 线程池
├── book-service 调用（最多 10 个线程）
├── user-service 调用（最多 5 个线程）
└── 剩余线程用于其他操作

如果 book-service 故障，只影响自己的 10 个线程
不会耗尽 user-service 的线程
```

### 5. Timeout（超时控制）

**作用**：避免长时间等待。

**超时设置原则**：
- 客户端超时 < 服务端超时 < 负载均衡器超时
- 例如：客户端 1s → 服务端 2s → Traefik 10s

### 6. Fallback（降级）

**作用**：返回兜底数据而非报错。

**降级策略**：
- 返回缓存数据
- 返回默认值
- 返回部分结果
- 调用备用服务

## 在我们的项目中的应用

### 当前架构的风险点

```
order-service
  ├── gRPC → book-service  (获取图书、扣减库存)
  │         └── 如果 book-service 宕机，订单创建全部失败
  ├── gRPC → user-service  (获取用户信息)
  │         └── 如果 user-service 宕机，无法验证用户
  └── HTTP ← Traefik       (接收用户请求)
            └── 如果无流量控制，高并发会压垮服务
```

### Day 9 的解决方案

| 层级 | 模式 | 实现方式 |
|------|------|----------|
| **gRPC Client** | 熔断器 | `sony/gobreaker` + gRPC 拦截器 |
| **gRPC Client** | 重试 | 指数退避 + gRPC 拦截器 |
| **gRPC Client** | 限流 | 令牌桶 + gRPC 拦截器 |
| **HTTP 网关** | 限流 | Traefik `rate-limit` 中间件 |
| **HTTP 网关** | 熔断 | Traefik `circuit-breaker` 中间件 |
| **HTTP 网关** | 重试 | Traefik `retry` 中间件 |
| **监控** | 指标 | Prometheus + Grafana |

## 拦截器链的执行顺序

gRPC 拦截器链（Client Side）：

```
请求进入
  → Tracing (创建 span，注入 trace context)
    → CircuitBreaker (检查熔断状态)
      → Retry (失败时重试)
        → RateLimiter (检查是否超限)
          → 实际 RPC 调用
        ← RateLimiter 结果
      ← Retry 结果
    ← CircuitBreaker 结果
  ← Tracing 结果
返回响应
```

**为什么这个顺序？**
1. **Tracing 最外层**：无论成功失败，都需要记录 trace
2. **CircuitBreaker 次之**：如果熔断器 Open，直接失败，不需要重试
3. **Retry 内层**：重试时每个 attempt 都会被 RateLimiter 检查
4. **RateLimiter 最内层**：每次调用（包括重试）都要限流

## 总结

容错不是可选的装饰，而是微服务架构的**必需品**。Day 9 我们将实现：

1. **gRPC 拦截器层**：熔断器 + 重试 + 限流
2. **HTTP 网关层**：Traefik 限流 + 熔断 + 重试
3. **监控层**：Prometheus 指标 + Grafana Dashboard
4. **验证**：故障注入测试，观察容错机制生效
