# Day 10 - 微服务认证：为什么需要集中式认证？

## 为什么需要认证？

在微服务架构中，认证是**第一道安全防线**。没有认证，任何人都可以冒充用户访问系统。

### 传统认证的问题

```
当前架构（自定义 JWT）：
┌─────────────────────────────────────────────────────┐
│                    Traefik                          │
│  (无认证检查，直接转发)                               │
└─────────────────────────────────────────────────────┘
        │                           │
        ▼                           ▼
┌───────────────┐           ┌───────────────┐
│ user-service  │           │ order-service │
│ ┌───────────┐ │           │ ┌───────────┐ │
│ │ JWT验证   │ │           │ │ JWT验证   │ │
│ │ (重复代码)│ │           │ │ (重复代码)│ │
│ └───────────┘ │           │ └───────────┘ │
└───────────────┘           └───────────────┘
```

**问题**：
1. **代码重复**：每个服务都独立实现 JWT 验证逻辑
2. **安全风险**：JWT secret 分散在多个服务中
3. **功能有限**：无法支持社交登录、MFA、账户恢复
4. **维护困难**：修改认证逻辑需要更新所有服务

### 集中式认证架构

```
目标架构（Ory Kratos + Oathkeeper）：
┌─────────────────────────────────────────────────────┐
│                    Traefik                          │
│  ┌─────────────────────────────────────────────┐   │
│  │         ForwardAuth Middleware              │   │
│  │         → Oathkeeper /decisions            │   │
│  └─────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
        │                           │
        ▼                           ▼
┌───────────────┐           ┌───────────────┐
│ user-service  │           │ order-service │
│ (无需JWT验证) │           │ (无需JWT验证) │
│ 读取header即可│           │ 读取header即可│
└───────────────┘           └───────────────┘

认证流程：
1. 用户登录 → Kratos 验证 → 颁发 session token
2. 用户访问 API → Traefik → Oathkeeper 验证 session
3. Oathkeeper 注入 JWT header → 转发到后端服务
4. 后端服务读取 header 中的用户信息（无需验证）
```

## Ory 组件介绍

### Ory Kratos - 身份管理

**职责**：管理用户身份的全生命周期
- 用户注册（邮箱/密码、社交登录）
- 用户登录（密码验证、多因素认证）
- 会话管理（session token、cookie）
- 账户恢复（忘记密码、邮箱验证）

**关键概念**：
- **Identity**：用户身份，包含 traits（邮箱、用户名等）
- **Session**：用户会话，包含 identity 信息和过期时间
- **Flow**：自服务流程（注册、登录、设置）

**端口**：
- `4433`：公共 API（用户访问）
- `4434`：管理 API（管理员操作）

### Ory Oathkeeper - API 认证代理

**职责**：在网关层统一处理认证
- 验证请求中的 session/JWT
- 根据访问规则决定是否放行
- 注入用户信息到请求头

**关键概念**：
- **Access Rule**：访问规则，定义哪些路由需要认证
- **Authenticator**：认证器，验证 session/JWT
- **Mutator**：变换器，注入用户信息到请求头

**端口**：
- `4455`：API + Decision API
- `4456`：代理端口（转发请求）

## 认证流程详解

### 1. 用户注册流程

```
用户 → Kratos 公共 API → 创建 identity → 返回 session token
```

### 2. 用户登录流程

```
用户 → Kratos 公共 API → 验证凭证 → 颁发 session token（cookie）
```

### 3. API 访问流程

```
用户 → Traefik → Oathkeeper Decision API → 验证 session → 注入 JWT → 后端服务
```

## 优势对比

| 特性 | 自定义 JWT | Ory 方案 |
|------|-----------|----------|
| 代码重复 | 每个服务独立实现 | 集中在 Oathkeeper |
| 安全性 | secret 分散 | 统一管理 |
| 功能 | 基础 JWT | 社交登录、MFA、账户恢复 |
| 维护成本 | 高 | 低 |
| 扩展性 | 差 | 好 |
