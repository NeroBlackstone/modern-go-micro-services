# API Gateway 核心概念

## 什么是 API Gateway

API Gateway 是微服务架构中的 **统一入口点**，所有客户端请求先经过 Gateway，再由 Gateway 转发到后端具体服务。

```
客户端 (Web / App / 第三方)
        │
        ▼
   ┌─────────────┐
   │ API Gateway  │  ← 统一入口
   └─────┬───────┘
    ┌────┼────┐
    ▼    ▼    ▼
  user  book  order  ← 后端微服务
```

## 解决什么问题

### 1. 客户端耦合

**没有 Gateway 时：**
```
客户端需要知道：
  - user-service 的地址和端口
  - book-service 的地址和端口
  - order-service 的地址和端口
  - 每个服务用什么协议 (HTTP/gRPC)
```

**有 Gateway 后：**
```
客户端只需要知道：
  - Gateway 的地址 (一个)
  - 统一的 HTTP 协议
```

### 2. 横切关注点重复

每个服务都需要实现的功能：
- 认证鉴权（验证 JWT Token）
- 限流（防止恶意请求）
- 日志记录
- HTTPS 终止

Gateway 统一处理这些，服务只关注业务逻辑。

### 3. 协议不一致

微服务间可能用不同协议：
- 对外：HTTP/HTTPS（客户端友好）
- 内部：gRPC（高性能）

Gateway 负责协议转换，客户端无需关心。

### 4. 请求聚合

前端展示一个页面可能需要调用多个服务：
```
订单详情页 = 订单服务 + 图书服务 + 用户服务
```

Gateway 可以聚合多个服务的响应，返回给客户端一个完整结果。

## 核心能力

| 能力 | 说明 |
|------|------|
| **路由转发** | 根据 URL 路径将请求转发到对应服务 |
| **负载均衡** | 同一服务有多个实例时，分配请求 |
| **认证鉴权** | 验证 Token，拦截未授权请求 |
| **限流熔断** | 保护后端服务不被打垮 |
| **协议转换** | HTTP ↔ gRPC |
| **请求聚合** | 合并多个服务的结果 |
| **日志监控** | 统一记录请求日志和指标 |

## 主流方案对比

| 方案 | 语言 | 特点 | 适用场景 |
|------|------|------|---------|
| **Traefik** | Go | Docker/K8s 原生支持，配置简单 | 容器化环境 |
| **Kong** | Lua/Nginx | 最成熟，插件生态丰富 | 企业级 |
| **APISIX** | Lua/Nginx | 性能极高，国内社区活跃 | 高并发 |
| **Envoy** | C++ | 云原生标配，Istio 数据面 | K8s + 服务网格 |

## 在我们项目中的位置

```
                    ┌─────────────┐
                    │   Traefik    │  ← API Gateway (端口 80)
                    │  (Day 6)    │
                    └──────┬──────┘
                           │
            ┌──────────────┼──────────────┐
            ▼              ▼              ▼
      ┌──────────┐  ┌──────────┐  ┌──────────┐
      │   user   │  │   book   │  │  order   │
      │ service  │  │ service  │  │ service  │
      └──────────┘  └──────────┘  └──────────┘
           │              │              │
      ┌────┴────┐   ┌────┴────┐   ┌────┴────┐
      │ Consul  │   │ Consul  │   │ Consul  │  ← 服务发现 (Day 5)
      └─────────┘   └─────────┘   └─────────┘
```

- **Traefik**：处理外部 HTTP 请求，路由到对应服务
- **Consul**：处理服务间 gRPC 通信的服务发现
- 两者职责不同，互不冲突
