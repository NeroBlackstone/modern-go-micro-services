# Day 14 - Vault：为什么微服务需要密钥管理？

## 问题：密钥到处散落

回顾之前的代码，我们的密钥分布在哪里：

```yaml
# configs/book-service.yaml
database:
  password: bookstore123    # ← 硬编码在配置文件中

service_auth:
  shared_secret: "${SERVICE_AUTH_SECRET}"  # ← 环境变量，但有默认值

# configs/order-service.yaml
rabbitmq:
  password: guest           # ← 硬编码
jwt:
  secret: your-secret-key-change-in-production  # ← 硬编码
```

```yaml
# compose.yml
environment:
  - SERVICE_AUTH_SECRET=${SERVICE_AUTH_SECRET:-super-secret-key-change-in-production}  # ← 默认值硬编码
```

**这些问题意味着什么？**

1. **密码泄露风险**：任何能访问 Git 仓库的人都能看到所有密码
2. **无法审计**：谁在什么时候读取了什么密钥？没有记录
3. **无法轮换**：修改密码需要重启所有服务
4. **环境不一致**：开发、测试、生产环境的密钥管理方式不同
5. **合规问题**：等保、SOC2 等合规要求密钥集中管理

## 密钥管理的演进

```
阶段一：硬编码                    阶段二：环境变量                   阶段三：密钥管理服务
┌─────────────────┐            ┌─────────────────┐            ┌─────────────────┐
│ 代码里写死密码   │    →       │ docker-compose  │    →       │ Vault 集中存储   │
│ Git 仓库泄露    │            │ 环境变量注入     │            │ 动态凭证         │
│ 无法轮换        │            │ 比硬编码好一点   │            │ 审计日志         │
└─────────────────┘            └─────────────────┘            └─────────────────┘
```

## HashiCorp Vault 是什么

Vault 是一个密钥管理工具，核心功能：

```
┌──────────────────────────────────────────────────────────┐
│                    HashiCorp Vault                       │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. 密钥存储（KV Engine）                                │
│     安全存储密码、API Key、证书等                          │
│     支持版本化，可以回滚                                  │
│                                                          │
│  2. 动态密钥（Dynamic Secrets）                          │
│     按需生成临时凭证（如数据库账号）                        │
│     自动过期，无需手动轮换                                │
│                                                          │
│  3. 数据加密（Transit Engine）                            │
│     加密即服务，应用无需管理加密密钥                        │
│                                                          │
│  4. 身份认证（Auth Methods）                              │
│     Token、AppRole、Kubernetes、LDAP 等多种认证方式        │
│     服务用身份证明换取临时 token                           │
│                                                          │
│  5. 审计日志（Audit Log）                                 │
│     记录所有操作：谁、何时、访问了什么                      │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## 核心概念

### Vault Server

```
┌──────────────────────────────────────┐
│           Vault Server               │
│                                      │
│  ┌────────────┐  ┌────────────────┐  │
│  │   Storage   │  │    Mem/Cache   │  │
│  │  (加密存储) │  │   (明文缓存)   │  │
│  └────────────┘  └────────────────┘  │
│                                      │
│  ┌────────────┐  ┌────────────────┐  │
│  │    Auth     │  │   Secrets      │  │
│  │   Methods   │  │   Engines      │  │
│  └────────────┘  └────────────────┘  │
│                                      │
│  ┌────────────┐  ┌────────────────┐  │
│  │  Policies   │  │   Audit Log    │  │
│  │  (权限控制)  │  │  (审计日志)    │  │
│  └────────────┘  └────────────────┘  │
└──────────────────────────────────────┘
```

### 认证流程（Auth Methods）

```
服务启动                    Vault
  │                          │
  │ 1. 发送 role_id +        │
  │    secret_id             │
  │ ────────────────────────▶│
  │                          │ 2. 验证凭证
  │                          │ 3. 检查策略
  │ 4. 返回临时 token        │
  │ ◀────────────────────────│
  │                          │
  │ 5. 使用 token 读取密钥   │
  │ ────────────────────────▶│
  │                          │ 6. 验证 token + 策略
  │ 7. 返回密钥数据          │
  │ ◀────────────────────────│
```

### AppRole 认证（生产环境推荐）

AppRole 是 Vault 为机器/服务设计的认证方式：

```
┌─────────────┐    role_id     ┌─────────────┐
│   Service   │ ──────────────▶│    Vault    │
│             │   secret_id    │             │
│  (启动时)   │ ──────────────▶│  验证身份   │
│             │                │             │
│             │ ◀──────────────│  返回 token │
│             │   client_token │             │
└─────────────┘                └─────────────┘
```

| 概念 | 说明 |
|------|------|
| `role_id` | 角色标识符（类似用户名），固定不变 |
| `secret_id` | 角色密钥（类似密码），可以轮换 |
| `token` | 临时访问凭证，有过期时间 |
| `policy` | 权限策略，控制能访问哪些路径 |

> **本项目当前实现：** Dev 模式下使用 `VAULT_TOKEN` 直接认证，简化学习流程。
> 生产环境应改用 AppRole 认证，实现最小权限和凭证轮换。

### Secrets Engine（密钥引擎）

```
KV Engine（静态密钥）                    Database Engine（动态密钥）
┌─────────────────────┐                ┌─────────────────────┐
│ secret/              │                │ database/            │
│   ├── database/      │                │   ├── postgres/      │
│   │   ├── book       │                │   │   ├── static/    │
│   │   └── order      │                │   │   └── dynamic/   │
│   ├── rabbitmq       │                │   └── mysql/         │
│   ├── jwt            │                │                      │
│   └── service-auth   │                │  Vault 自动生成       │
│                      │                │  临时数据库账号        │
│  手动写入/读取        │                │  自动过期销毁          │
│  适合：密码、API Key  │                │  适合：数据库连接      │
└─────────────────────┘                └─────────────────────┘
```

## 本项目的 Vault 方案

```
┌──────────────────────────────────────────────────────────┐
│                    密钥存储层                              │
│                                                          │
│  Vault (Dev Mode)                                        │
│  ├── secret/database/book    (book 数据库凭证)            │
│  ├── secret/database/order   (order 数据库凭证)           │
│  ├── secret/rabbitmq         (RabbitMQ 凭证)             │
│  ├── secret/jwt              (JWT 签名密钥)               │
│  └── secret/service-auth     (服务间认证密钥)              │
│                                                          │
├──────────────────────────────────────────────────────────┤
│                    认证层                                  │
│                                                          │
│  Token（Dev 模式）/ AppRole（生产环境）                     │
│  ├── book-service  → 读取 database/book, service-auth     │
│  ├── order-service → 读取 database/order, rabbitmq, jwt   │
│  └── admin-service → 读取 database/order, jwt             │
│                                                          │
├──────────────────────────────────────────────────────────┤
│                    服务层                                  │
│                                                          │
│  启动时：Token 认证 → 读取密钥 → 覆盖本地配置                │
│  运行时：使用 Vault 提供的密钥连接数据库/消息队列             │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## 为什么选择 KV Engine + Token 认证

对于学习项目，这是最佳组合：

1. **KV Engine**：最简单的密钥存储，手动写入即可，适合学习
2. **Token 认证**：Dev 模式下最简单，无需额外配置（生产环境改用 AppRole）
3. **优雅降级**：Vault 不可用时，服务仍能用本地配置启动
